# Feature: Search & Navigation

← back to [features index](README.md) · [reference index](../README.md)

Covers search, pan/zoom, `/person/:slug` deep links, the Members page, and orientation. Stores: [`uiStore`](../../../src/frontend/src/stores/uiStore.ts) (`orientation`, `search`, `searchCursor`), [`familyStore`](../../../src/frontend/src/stores/familyStore.ts) (`focusId`), plus selection/panel stores from [person-details.md](person-details.md#stores).

## Routing & deep links ([`router/index.ts`](../../../src/frontend/src/router/index.ts), [`views/TreeView.vue`](../../../src/frontend/src/views/TreeView.vue))
History mode: `createWebHistory()` (no hash).

| Path | Name | Component |
|---|---|---|
| `/` | `tree` | `TreeView` |
| `/chronicle` | `chronicle` | `ChronicleView` |
| `/members/:slug?` | `members` | `MembersView` |
| `/person/:slug` | `person` | `TreeView` |

**`/person/:slug` behavior:**
- The slug is `<given>-<middle>-<surname>-<birthYear>-<id>`, e.g. `/person/peter-yanovich-kowalski-1780-p-0003` (the middle-name/patronymic segment is omitted when the person has none, e.g. `franciszek-kowalski-1788-p-0003`). The name is the **English** name (or a Cyrillic→Latin transliteration of `ru`/`be` when `en` is absent), diacritics folded to ASCII; the birth year is omitted when unknown.
- **Resolution is frontend-only** ([`utils/personSlug.ts`](../../../src/frontend/src/utils/personSlug.ts)): the trailing `p-<digits>` id is the source of truth — `extractPersonId` recovers it and the existing `GET /api/people/{id}` fetches the person. The name part is decorative; a truncated or stale name still resolves.
- **Backward compatible:** legacy `/person/p-0003` links still work (the bare id is a valid trailing-id match), and the URL self-heals to the canonical slug via `router.replace` once the person summary is loaded.
- Valid id → person panel expands in the rail and `selection.open(id)` fetches detail. (Entering via the URL does **not** open the popup — only desktop tree-node clicks do.)
- Invalid/unknown id → fetch fails; `selectionStore.error` is set and shown in the panel; the panel still opens with the raw id.

**URL ⇄ selection sync (two-way):**
- URL → store: a watcher extracts the id from the slug and drives `openPerson` / `minimizeAllPersons`.
- Store → URL: expanding a person `router.replace`s to the canonical `/person/:slug`; clearing replaces back to `/`.
- Tree-node click `router.push`es `/person/:slug` (adds history). A guard prevents redundant double-navigation.
- **Clicking a person on the tree never moves the camera** — it only selects. The one-shot arrival glide is armed solely when `TreeView` *mounts* on `/person/:slug` (a deep link, or the Members page's **Find on tree**); mounting on the bare `/` route disarms it, so an ordinary click can't consume it and pan the tree.
- Browser **Back** from `/person/:slug` → `/` clears the selection and closes detail.

## Members page (read-only) {#members-page-readonly-membersslug}

`/members/:slug?` ([`views/MembersView.vue`](../../../src/frontend/src/views/MembersView.vue)) is a searchable master-detail roster, separate from the oak tree. It shares the same friendly-slug scheme as `/person/:slug` (`personSlug`/`extractPersonId`) for its optional `:slug` param, so a Members deep link is shareable the same way.

**Layout:** a two-column grid — a **roster index** ([`MembersIndex.vue`](../../../src/frontend/src/components/MembersIndex.vue)) on the left, a **per-person dossier** ([`MemberDetail.vue`](../../../src/frontend/src/components/MemberDetail.vue)) on the right. Below the app's mobile boundary (the [`MOBILE_MEDIA_QUERY`](../../../src/frontend/src/composables/useMediaQuery.ts) predicate `(max-width: 1199.98px), (max-height: 559.98px)` — the same threshold the tree rail collapses at) the two panes can't comfortably share the viewport, so the page **drills down**: the roster is full-screen until a person is picked, then the dossier is full-screen with a **Back to list** button (`data-test="members-back"`) that clears the slug and returns to the roster. The roster stays mounted (hidden via `v-show`) across the drill-down, so its search/filter state survives the round-trip. Selecting a roster row or a relative chip `router.push`es the canonical `/members/:slug`, so Back/forward navigate between selections. With no selection on a wide viewport, a hint prompts picking someone.

**Roster index:** a live substring search box (`data-test="members-search"`, same [`personMatchesQuery`](#search-membersvue-composablesusesearchmatchests) predicate as the tree's nav-bar search) plus a chip row beneath it — a **surname** filter (`data-test="filter-surname"`, distinct localized surnames), a **sort** control (`data-test="filter-sort"`) — **by birth year (the default, oldest first)** or **name A–Z** (which sorts by surname, then given name within each surname, so a single-family roster reads as a clean given-name A–Z) — and a **Clear** button (`data-test="filter-clear"`, shown only when a search/filter/non-default sort is active — i.e. the sort is no longer birth year). Each row shows a thumbnail (or an empty placeholder), full name, and a `birth – death` year span; an empty-state message (`data-test="members-empty"`) shows when nothing matches (no match-count footer). (The mockup's Generation and Place filters are deferred — Place needs residence data not carried in the roster payload.)

**Dossier ([`MemberDetail.vue`](../../../src/frontend/src/components/MemberDetail.vue)):** fetches `GET /api/people/{id}` fresh on selection (not the summary already in the store) to get full detail. A framed portrait medallion + name + `née …` + lifespan sit beside a **Find on tree** button that navigates to `/person/:slug` and glides the oak camera to that person on arrival. Below, **field tablets grouped into rows** — names (given name, **middle name** = patronymic/Отчество, surname, and **maiden name**), then **Born** / **Died** (date + place) on their own row, then **Sex** + **Vocation** on a row below the dates. The **maiden-name** tablet (and the header's `née …` line) is shown **only for non-male persons** — it's hidden entirely for males, in both the read-only view and the editor. Names render as **`Given Middle Surname`** throughout the app (roster, dossier header, tree medallions, popup) via `formatPersonName`, dropping the middle name when absent. A signed-in editor sees an **Edit details** button (`data-test="fields-edit"`) in the dossier header's **top-right corner** (separate from Find on tree) that swaps the read-only tablets for [`MemberFieldsEditor`](../../../src/frontend/src/components/MemberFieldsEditor.vue) — tabbed ru/be/en name inputs, sex/vocation dropdowns, and **birth/death date inputs (year + month + day)**, with a resilient Save (copies `BiographyEditor`: dirty-gated, buffers kept on failure, confirm-on-discard) that posts to `PUT /api/people/{id}/profile`. The date inputs are **progressive** — month is disabled until a year is entered, day until a month is entered, and clearing a unit cascades down — so a submitted date stays coherent. **Only changed fields override:** the editor takes the current sparse override as its payload base and submits `override ∪ edits`, so untouched fields keep inheriting the `family.json` seed; a **reset** (`↺`) clears an override back to the seed — per-field for the scalar fields, and **per-event** for the birth/death date (one control clears its whole year+month+day). After a successful save the store patches names/sex/vocation in place, refetches the graph only when **birth year** changed (so the oak re-lays-out), and recomputes the `/members/:slug` URL. Then **Biography** — **editable** by a signed-in editor via an edit affordance (`data-test="bio-edit"`) on the section header that opens the same tabbed ru/be/en [`BiographyEditor`](../../../src/frontend/src/components/BiographyEditor.vue) used in the tree popup (`PUT /api/people/{id}/biography`; independent of the field editor) — and **Residences** side-by-side in double-bordered gilt panels, **also editable** (cut 1c — see [Editing residences](#editing-residences-signed-in-editors-cut-1c) below), then the same read-only [photo grid](person-details.md#photo-grid) used elsewhere (`can-edit` forced `false` here).

### Editing residences (signed-in editors, cut 1c)

A signed-in editor sees its own edit affordance (`data-test="residences-edit"`) on the **Residences** panel header, separate from the **Biography** editor but **mutually exclusive with the scalar Edit details editor** (opening one closes the other — see **Save / revert** below for why) — clicking it swaps the read-only list for [`ResidencesEditor.vue`](../../../src/frontend/src/components/ResidencesEditor.vue). Each row holds a place name per locale (`data-test="place-ru-{i}"`/`place-be-{i}`/`place-en-{i}`, at least one non-blank locale required), a `fromYear`/`toYear` span, a map-pin icon button ([`MapPinIcon.vue`](../../../src/frontend/src/components/MapPinIcon.vue), `data-test="pick-{i}"`) that opens an inline map picker for that row (only one row's picker is open at a time), and a remove button (`data-test="remove-{i}"`). Rows are added with `data-test="add-residence"`; the client applies **no cap** on adding rows — exceeding the server's 10-row limit surfaces the `PUT` 400 on save, not a disabled Add button. A rejected save routes each message **back to the row that caused it** (`data-test="row-error-{i}"`, `role="alert"`): the API's `fieldErrors[].propertyName` is `Profile.Residences[{i}]` or `Profile.Residences[{i}].{Field}` (pinned server-side by `UpdatePersonProfileValidatorTests`), and the index maps 1:1 onto the visible rows. Failures outside the residence list (e.g. `Profile.BirthYear`) stay form-level (`data-test="residences-form-error"`), and the generic "save failed" line is suppressed whenever a more specific message is already shown. Removing a row clears the row messages rather than let a stale index label the wrong row.

**Map picker ([`MapPicker.vue`](../../../src/frontend/src/components/MapPicker.vue)):** when the build-time `VITE_GOOGLE_MAPS_API_KEY` env var is configured, it shows a debounced (350 ms) free-text city search — up to 5 candidates — and an interactive Google Map (Maps JS) with a draggable pin (default center Minsk, 53.9/27.56, when the row has no coordinates yet). Search, reverse geocoding, and localized-name lookup all call our own **editor-gated backend proxy** (`GET /api/geocode/search|reverse|names`, see [features/backend-api.md](backend-api.md#get-apigeocodesearch-get-apigeocodereverse-get-apigeocodenames)) rather than Google's Geocoding web service directly — the browser never holds a geocoding-capable key. Picking a search result or dragging the pin fills `lat`/`lng`, looks up the locality name in all three locales via the `names` proxy endpoint and fills any locale the picker actually resolved (leaving a locale the editor already typed untouched if the lookup returns nothing for it), and derives a keyless `mapUrl`. **Picking a result frames the whole place**, not its centre point: the search response carries Google's `viewport` bounds and the picker calls `fitBounds` with them, so a city fills the map; a result without a viewport falls back to a fixed locality zoom (11). Because the marker is anchored on the place's centre — exactly where the basemap draws the locality label, so the pin hides the name being confirmed — the picker also echoes the chosen place name in its own caption below the map (`data-test="map-chosen"`). Plain manual **latitude/longitude number inputs** (`data-test="manual-lat"`/`manual-lng"`) are **always available**, alongside the map when one is configured — a keyboard-only or screen-reader editor can enter exact coordinates without depending on mouse pin-drag, and typing a value there recenters the map and repositions the pin when both exist. **Without a configured key, or if the Maps script fails to load** (a 10 s timeout bounds a hung script load), the manual inputs are the *only* input method — local dev and CI run keyless by default, and the manual path still derives the same `mapUrl` from the typed coordinates. A debounced search request superseded by a newer one (the editor kept typing before the first reply arrived) is discarded, so results never flash back to a stale query.

**Save / revert:** Save (`data-test="residences-save"`) posts the **whole** residences list through the existing `PUT /api/people/{id}/profile` (no new endpoint) — a **whole-list replace**, not a per-row patch; `null` inherits the `family.json` seed list, a present (possibly empty) list replaces it wholesale. A **Reset to seed** button (`data-test="residences-revert"`, shown only while a residences override currently exists) sends `residences: null` on the next save. Queuing a reset does **not** blank the list — the seed list isn't fetchable client-side (`PersonDetail.residences` is already seed-merged and the profile override only carries the override), so an emptied list would read as "the seed is empty" rather than "these rows are about to go". Instead the rows stay on screen struck through and `inert`, above a notice (`data-test="residences-revert-notice"`) explaining what saving will do, with an **Undo reset** (`data-test="residences-revert-undo"`) that cancels it; while a reset is queued the Add and Reset buttons are hidden. Because the profile override is one whole-record document, both editors carry the field they don't own forward unchanged in their payload — the residences editor sends the current scalar override fields untouched, and `MemberFieldsEditor`'s scalar save likewise carries the current `residences` value through — so saving one never wipes an override made by the other. That carry-forward only holds while each editor's snapshot is fresh, which is why the two are **mutually exclusive in the UI** ([`MemberDetail.vue`](../../../src/frontend/src/components/MemberDetail.vue) `openFieldsEditor`/`openResidencesEditor`): each snapshots its payload base once when opened, so leaving both open would let the second save carry a pre-edit snapshot of the first's field and silently undo it. Opening one closes the other, discarding the stale window.

**Read-only view (visitors, and editors when not editing):** each residence row shows the place name, `{from}–{to|present}` year span, and — only when the row has a `mapUrl` — a map-pin icon link ([`MapPinIcon.vue`](../../../src/frontend/src/components/MapPinIcon.vue), `data-test="residence-map-link"`, `target="_blank" rel="noopener noreferrer"`, shared `person.viewOnMap` label with the pre-existing tree-popup residence link) that opens Google Maps in a new tab. This is a **plain outbound hyperlink built client-side from the stored coordinates** ([`buildMapUrl`](../../../src/frontend/src/maps/mapLink.ts)) — never an embedded map, and not a Google API call, so a visitor viewing residences never triggers billed Maps usage; only the editor's picker (city search + map tiles) does.

**After save:** the dossier's local `detail` and the tree's [`selectionStore`](person-details.md#stores) cache both update in place (`selection.applyDetail`) — unlike a birth-year scalar edit, there is **no** graph refetch and **no** `/members/:slug` recompute, because residences affect neither the oak layout nor the person-slug URL.

**Immediate-family cluster ([`MemberFamilySheet.vue`](../../../src/frontend/src/components/MemberFamilySheet.vue), [`composables/useRelatives.ts`](../../../src/frontend/src/composables/useRelatives.ts)):** a **bottom sheet** overlaying the dossier (owned by `MembersView`, not the scrolling dossier). It is **collapsed by default** (just the handle, `data-test="family-sheet-handle"`) so it never occludes the biography; clicking the handle expands it to reveal the whole family (parents, spouse(s), siblings, children), and it re-collapses when a different person is selected. The handle is disabled only when the person has no recorded relatives. Only non-empty groups render, as clickable chips (portrait thumb — or an initial when there's no photo — + name + year span); clicking a chip selects that relative. `deriveRelatives` is pure/side-effect-free: siblings share at least one parent id (half-siblings included, self excluded); spouses/children come from any union that includes the person; each group sorts by birth year then id.

**Editable so far (cuts 1a/1b/1c):** scalar fields (`MemberFieldsEditor`), biography (`BiographyEditor`), and residences + the map picker (`ResidencesEditor`) all have in-app editors, as described above. **Still read-only / unbuilt:** the photo grid is intentionally display-only here (`can-edit` forced `false` — edit a person's photos from the tree popup instead, see [person-details.md](person-details.md#photo-grid)); birth/death **place** editing is deferred (the scalar editor is years-first); no add/remove-relative or relationship-editing controls exist yet — that's **cut 2**.

**Entry point:** the **Members** tab in the app bar now navigates here (previously a disabled placeholder) — see [features/app-shell-and-localization.md](app-shell-and-localization.md#tabs-tabnavvue).

## Pan / zoom ([`interactions/panZoom.ts`](../../../src/frontend/src/interactions/panZoom.ts), [`usePanZoom.ts`](../../../src/frontend/src/interactions/usePanZoom.ts))
| Input | Effect |
|---|---|
| Mouse wheel | Zoom about the cursor (`exp(−deltaY*0.0015)`) |
| Left-drag | Pan — only after a **4 px** threshold (so a click still selects); pointer capture acquired then |
| 1-finger touch | Pan |
| 2-finger touch | Pinch-zoom about the midpoint |

- **Zoom limits:** scale `0.2`–`6.0`.
- **No on-screen zoom buttons.** SVG uses `touch-action: none` and prevents default on `touchmove`.
- **Initial framing (`fit`):** frames the **default-root family** — the `isDefaultRoot` person plus two descendant generations (children + grandchildren) and each tier's co-parents, via a depth-2 BFS in [`focusBounds.ts`](../../../src/frontend/src/layout/focusBounds.ts) (`defaultRootFocusBounds`; falls back to the 2-most-recent-generation band when there is no default root). 60 px padding, capped at natural size (`maxScale: 1`) so it never over-zooms on large screens. The oak starts at opacity 0 and fades in after the first fit.
  - **Desktop** fits the whole box (`contain`). **Mobile-class viewports** (the mobile predicate) fit the box's **short time/generation axis** and let the wider sibling spread overflow (pannable) so cards stay legible instead of letterboxing to an unreadable scale; the overflowing axis is **anchored on the root** so gen0 stays in view, and only when that axis actually overflows.
- **Re-fit:** on container resize **only if the user hasn't adjusted the camera**; on orientation switch, **always** (coordinate space transposes).

## Search ([`SearchField.vue`](../../../src/frontend/src/components/SearchField.vue), [`composables/useSearchMatches.ts`](../../../src/frontend/src/composables/useSearchMatches.ts)) {#search-membersvue-composablesusesearchmatchests}
A live, client-side, case-insensitive substring search. The predicate ([`personMatchesQuery`](../../../src/frontend/src/composables/useSearchMatches.ts)) is shared between the tree's nav-bar search and the [Members roster](#members-page-readonly-membersslug) search.

**Matches against** (in the current locale): given name, surname, **maiden name**, **middle name** (patronymic), `"given surname"`, `"surname given"`, and `"given middle surname"`.

**UI ([`SearchField.vue`](../../../src/frontend/src/components/SearchField.vue)):**
- `<input type="search">` (`data-test="search-input"`).
- Counter (`data-test="search-count"`): `"1 / N"` with matches; `"0"` (faint) when a query has no match; hidden when empty.
- Enter-hint `↵` shown only when there is more than one match.
- Placeholders — ru: `Поиск по имени…`, be: `Пошук па імені…`, en: `Search by name…`.

**Behavior:**
- Match order: youngest first by `birthYear` (null years last).
- **Typing** debounces 300 ms before the camera moves; **Enter** advances the cursor immediately and cycles (wraps around) through matches.
- The camera **glides** (0.35 s) to center the current match; if zoomed below the readable threshold (`k < 0.8`), it jumps to `k = 1`.
- Search **never re-roots** the tree: because the whole connected family is always rendered ([oak-tree.md](oak-tree.md#layout-engine-treelayoutts)), every match is already on the canvas, so search only glides the camera.
- Matched medallions get the green-gold `--match` overlay (wins over selection).
- **No match:** counter `"0"`, no error, camera doesn't move, Enter is a no-op.
- **Clearing** resets `search` and `searchCursor`; highlights vanish; camera doesn't move.

Search state is session-only (not persisted; not in the URL).

## Orientation
`uiStore.toggleOrientation()` / `setOrientation()` flip vertical ↔ horizontal, persisted in `localStorage['familytree.orientation']` and restored on load. The toggle UI lives in the app bar (desktop) or the hamburger sheet (mobile) — see [app-shell-and-localization.md](app-shell-and-localization.md). Orientation is **not** carried in the URL (shared links don't preserve it).

**Responsive default:** until the user makes an explicit choice, orientation follows the viewport — **horizontal on mobile-class viewports** (the mobile predicate `(max-width: 1199.98px), (max-height: 559.98px)`, [`MOBILE_MEDIA_QUERY`](../../../src/frontend/src/composables/useMediaQuery.ts)), **vertical otherwise** — applied via `uiStore.applyResponsiveOrientation()` as the screen crosses the breakpoint. The moment the user toggles (or a stored orientation is restored), `orientationExplicit` is set and the responsive default **stops overriding** the manual choice for the rest of the session.

## QA notes
- Drag-then-release over a node must **not** select it (4 px threshold guards this).
- Enter keeps cycling even though the native `search` input re-fires its event (guarded in `uiStore.setSearch`).
- Re-issuing the same search target after a manual pan still re-centers (a sequence value forces it).
- Searching by a person's **maiden name** now surfaces them in both the tree nav-bar search and the Members roster — this was previously a non-match.
- A signed-in editor sees three edit affordances in the Members dossier — **Edit details** (scalar fields), the biography edit button, and the residences edit button. Biography saves through its own endpoint and is genuinely independent, but **Edit details and Residences are mutually exclusive**: both snapshot their `PUT /profile` payload base once at open, so opening one force-closes the other rather than letting a stale snapshot overwrite the other's just-saved change. An anonymous visitor sees the same dossier with none of the edit buttons rendered (`canEdit` gates them). No add/remove-relative or relationship-editing controls exist yet (cut 2).
- Residence rows have **no client-side cap** on Add — exceed the server's 10-row limit and Save surfaces the `PUT /api/people/{id}/profile` `400` inline rather than the button being disabled.
- The residence map picker is **editor-only and interactive-map-only in the picker** — the read-only residence list (shown to visitors, and to editors before clicking the residences edit button) never embeds a map, only a plain outbound link, so viewing residences never triggers a billed Google Maps load.
