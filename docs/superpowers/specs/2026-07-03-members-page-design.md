# Design: Members page — a browsable family roster that doubles as the editor's console

Generated by /office-hours on 2026-07-03
Branch: claude/festive-yonath-cd6b4a
Repo: family-tree (perovsky.family)
Status: APPROVED
Mode: Builder

## Problem Statement

The app renders the family as a spatial SVG oak (`/`) and a parchment stats cover
page (`/chronicle`). There is **no flat, findable index of everyone** — to reach a
person you navigate the tree or use nav-bar search that cycles the camera. And while
signed-in editors can already edit biographies and manage photos in-app, there is **no
in-app way to see or edit a person's core details** (names, dates, sex, vocation,
residences); those still live only in the `family.json` seed.

We want a **Members page**: a compact, inventive, theme-aware roster of every family
member that is the primary *findable* entry point into each person, and that doubles as
the signed-in editor's console for correcting a person's own fields. Each entry opens
into that person's immediate-family neighborhood — parents, siblings, spouse(s),
children — shown as clickable relatives, laid out so that **add/remove-relative
affordances slot in later without a redesign**.

## What Makes This Cool

It is not a CRUD admin table and it is not a second tree. It is a **master-detail family
catalog**: a compact searchable index on one side, and on the other a person's fields
(inline-editable) surrounded by their close family as a small spatial constellation —
parents above, siblings and spouse beside, children below. The relationship area holds
**reserved empty slots** that read as "there could be more here," which is exactly where
the future add/remove flow lands. You get a page you would actually show a relative
("here's everyone, here's how grandpa connects to us"), and the editor gets a fast way
to fix the birth year that has been wrong for three years — from the same surface.

North star (post-ship polish, not this cut): the index becomes an **animated census-card
catalog** that Flip-re-sorts by decade / surname / vocation / generation, and the opened
card lifts out while relatives fan around it. Banked, not built now.

## Constraints

- **Solo, personal project, "having fun" mode.** Ship something shareable; keep the
  dependency list lean.
- **Theme-aware.** Must re-skin with the active Film / Classic theme like medallions and
  the popup already do (SCSS design tokens in `src/styles/tokens.scss`).
- **Localized.** Names are `LocalizedText` (ru / be / en); the editor must handle all
  three locales; the roster must search/display in the active locale.
- **No writes to `family.json`.** Edits persist through the existing override layer only.
- **Stack:** .NET 10 API (MediatR + thin controllers + FluentValidation), Vue 3 + TS +
  Pinia + vue-router + vue-i18n.

## Premises

1. **New third route.** `/members` (with an optional `/members/:slug` deep link) joins
   `/` (tree) and `/chronicle`. — agreed.
2. **Each entry surfaces the immediate-family neighborhood** (parents, siblings,
   spouse(s), children) as clickable relatives that navigate/select within the page.
   Read-only in this cut, laid out so add/remove affordances slot in later. — agreed.
3. **Editing = a person's own scalar fields only** — given/surname/maiden name (× 3
   locales), sex, birth & death (year at minimum; place optional), vocation, and the
   **residences list** (place + from/to years + map URL). Bio + photos already have
   editors and stay as-is. Relationships stay seed-defined and are displayed but not
   editable. — agreed (residences added by the user).
4. **Edits persist by extending the append-only override layer** — a new "profile
   override" mirrors `IPersonOverrideStore`'s pattern (append revision, merge in
   `FamilySnapshotProvider`, never touch the seed). **Critical:** the override merges at
   the **snapshot layer**, so every consumer — `treeLayout.ts` / `timeScale.ts` and the
   era-frame picker — reads the corrected value. A Members-only read model is rejected:
   it would split-brain the birth year (Members says 1902, the oak still places 1898 with
   the wrong period frame). — agreed and sharpened by the cross-model review.
5. **Add-person and delete-person are deferred to a coherent cut 2** that also does
   relationship editing. Rationale: the override store only modifies existing seed ids; a
   net-new person is a different mechanism (the snapshot must *add* an entity), and a
   relationship-less new person is an orphan the oak cannot place. — agreed.

## Cross-Model Perspective

An independent Claude subagent reviewed a structured summary cold (no conversation
history):

- **Coolest version:** a "census card catalog that shuffles" — era-styled cards that
  animate-re-sort by decade / surname / vocation / generation, opened card lifts out and
  relatives fan around it. Reuses the theme system, the medallion render, and the
  existing Flip motion investment. (Banked as north star.)
- **Key insight — what the builder cares about:** the one emphasized phrase was *"a
  compact, INVENTIVE (not a boring table)."* Design the roster's *form* first; the
  persistence is a solved, copied pattern.
- **50% for free:** reuse vue-router + `PersonPopup` for detail; the existing
  `personMatchesQuery` predicate already covers the localized name fields. (Fuse.js was
  suggested for fuzzy/cross-script search; deferred — substring search is plenty for a
  personal archive of this size and keeps deps lean.) The genuinely new 50%: the
  immediate-family neighborhood cluster + the profile-override merge.
- **Riskiest thing (adopted into P4):** the profile-override merge must happen at the
  **snapshot layer**, because birth year drives both tree placement *and* card era
  styling. Merging only in a Members read model guarantees divergence that looks like a
  rendering bug. Decision: merge in `FamilySnapshotProvider`, exactly where biography and
  media overrides already merge.

## Approaches Considered

### Approach A: Grid + reuse the popup (minimal viable)
Responsive theme-aware grid of existing medallion cards on `/members`; clicking opens the
existing `PersonPopup` (already has bio editor + photo manager) with a relatives strip
added; facet sort via dropdown, no animation; search reuses `personMatchesQuery`.
- Effort **M** · Risk **Low**
- Pros: fastest; maximum reuse; only real new backend is the scalar-edit endpoint.
- Cons: "a grid that launches a popup," not the neighborhood surface described; does not
  build the cut-2 seams; least inventive.
- Reuses: PersonMedallion, PersonPopup, useSearchMatches, override pattern.

### Approach B: Master-detail catalog page (ideal — chosen)
Dedicated `/members/:slug?` two-pane page: a compact search-filtered index on the left
(sectioned by letter/decade), a detail pane on the right with the person's
inline-editable fields **and** the immediate-family neighborhood laid out spatially with
explicit reserved empty slots. Relatives are clickable and select within the page.
- Effort **L** · Risk **Med** (new neighborhood-cluster component; scalar field editor
  form; ru/be/en name-field i18n; residences editor).
- Pros: the exact compact/inventive master-detail described; the reserved slots are the
  cut-2 seams; deep-linkable; profile override merges at the snapshot layer.
- Cons: more build than A; the scalar-field editor (names/dates/sex/vocation/residences)
  is net-new.
- Reuses: override pattern (extended), vue-router, family store, search predicate, theme
  tokens.

### Approach C: The census-card catalog that shuffles (creative/lateral)
Approach B, but the index is the animated census-card catalog (Flip re-sort across facet
arrangements; card lift + relative fan on open).
- Effort **XL** · Risk **Med-High** (Flip motion over 100s of cards; raster/perf
  discipline required — see the Classic-theme raster lesson: bake bitmaps, never vector,
  in a pan/zoom canvas).
- Pros: highest "whoa"; leverages existing Flip motion; memorable to show family.
- Cons: most effort; motion perf risk on large trees; over-invests in polish before the
  editing plumbing is proven.
- Reuses: Flip motion work, era card styling, everything in B.

## Recommended Approach

**Approach B.** It is the surface the builder actually described ("entry to person
details… display close relatives and siblings… so that in future add/remove"), it
deliberately builds the seams cut 2 needs, and it banks C's expensive animated shuffle as
post-ship polish instead of betting the first cut on motion. The **residences editor**
ships in cut 1 as a plain list editor (place text per locale + from/to years); the
**map-based city picker** is a stretch that may ride with cut 2 because it pulls in a
geocoding/map dependency and a new interaction.

### Backend shape (shared by all approaches)
- Extend `IPersonOverrideStore` with a **profile override**: append-only, keyed by
  existing person id, carrying the editable scalar fields (names, sex, birth/death,
  vocation, residences). Mirror `AppendBiographyAsync` / `GetLatestBiographiesAsync` /
  `GetLatestBiographyAsync` (and the media equivalents) exactly.
- Implement in both stores: `FirestorePersonOverrideStore` (prod) and
  `InMemoryPersonOverrideStore` (local/tests).
- Merge in `FamilySnapshotProvider` alongside biography/media overrides, so the merged
  snapshot — and therefore layout, era styling, and the graph — all see corrected values.
- New endpoint `PUT /api/people/{id}/profile` on `PeopleController`, thin, behind the
  same editor auth as biography. MediatR command + FluentValidation validator
  (`UpdatePersonProfileCommand` / `Handler` / `Validator`), mirroring the biography trio.
- **Save refreshes the snapshot** the same way a biography save does (the merged snapshot
  is "refreshed on editor save," per CLAUDE.md), so the editor sees the change immediately
  rather than after the 10-min TTL.
- Validation: year ranges sane (birth ≤ death, plausible bounds), at least one locale set
  per name field (surname must not end up blank), residence from ≤ to.

### Override merge semantics (nail this before writing the merge)
- **Whole-record revision.** Each profile-override revision captures the *full editable
  field set as-of save* (snapshotted from the current merged state); the merge takes the
  latest revision wholesale (matches the biography pattern). This avoids a partial edit
  silently clobbering an unrelated field.
- **Per-field null/fallback for `LocalizedText`.** An **omitted / null** override locale
  **falls back to the seed** value; the override is not authoritative-blank. An explicit
  empty string that *hides* a seed value is **not representable in cut 1**. This protects
  the common cases: a legitimately-empty maiden name stays empty, but clearing `en`
  surname must never make the surname vanish (the validator rejects an all-null name).
  This is the same class of risk as the split-brain birth-year bug — resolve it in the
  merge, not later.

### Frontend shape (Approach B)
- `MembersView.vue` under `views/`; route `{ path: '/members/:slug?', name: 'members' }`.
  The slug resolves by its **embedded id**, so a stale slug still works; after a profile
  edit that changes name/birth year, recompute the canonical slug and `router.replace` the
  URL (same friendly-slug scheme as `/person/:slug`).
- Left index: a `MembersIndex` list — compact rows or small cards (portrait thumb + name
  + years), search-filtered via the existing **shared** `personMatchesQuery` predicate —
  extend it to also match maiden name, which then applies everywhere the predicate is used
  (Members index *and* the nav-bar tree search). Sectioned by first letter or birth
  decade. Selecting sets `:slug`.
- Field inputs: **sex** is an enum (dropdown, not free text); **vocation** is the existing
  vocation enum (dropdown, with its `VocationIcon`); names are three locale text inputs
  each; years are numeric inputs.
- Right detail: `MemberDetail` — reuses `PersonHeader`/portrait, shows fields; when a
  signed-in editor, fields become an inline editor form (`MemberFieldsEditor`, sibling in
  spirit to `BiographyEditor`) posting to `PUT /api/people/{id}/profile`.
- `RelativeCluster` — derives parents (from `parents`), siblings (shared parent),
  spouse(s) and children (from `unions`) client-side; renders them as clickable chips in a
  parents-above / siblings-spouse-beside / children-below layout, **with reserved empty
  "add" slots rendered but inert** (the cut-2 seam).
- `ResidencesEditor` — list of `{ place (ru/be/en), fromYear, toYear, mapUrl }` rows; map
  picker stubbed as a plain URL field in cut 1.
- Add a nav entry to the Members route (AppBar / TabNav), theme-aware.

## Open Questions

1. **Index density vs. cards.** Compact rows (fast to scan 100s) or small photo cards
   (prettier, more "wall")? Recommend rows with a leading thumbnail — compact *and*
   photographic. Settle in `/plan-design-review` or the visual sketch.
2. **Residences map picker in cut 1 or cut 2?** Recommend cut 2 (needs a geocoding/map
   lib + interaction design). Cut 1 keeps the existing `mapUrl` as an editable field.
3. **Place fields for birth/death** — edit in cut 1 or just years? Recommend years-first;
   places can join the residences-style editor later.
4. **Sibling definition** — full siblings (both parents shared) vs. half (one parent)?
   Recommend "shares at least one parent," visually distinguishing half-siblings later.
5. **Does the profile override need per-field revision history** like biography, or is
   last-write-wins per person enough? **Resolved:** append-only whole-record revisions,
   latest wins wholesale, each revision capturing the full editable field set as-of save
   (matches the existing pattern; simplest). See "Override merge semantics" above for the
   null/fallback rule that goes with this.

## Success Criteria

- `/members` lists every person; searching filters the index live in the active locale.
- Selecting a member deep-links (`/members/:slug`) and shows their fields + a clickable
  relative cluster; clicking a relative selects them.
- A signed-in editor can change a person's name/dates/sex/vocation/residences; the change
  **persists across reload** and is reflected in the **tree** (position + era frame) and
  everywhere else, not just on the Members page.
- A signed-out visitor sees the same roster and clusters read-only.
- Re-skins correctly under both Film and Classic themes.
- The relative cluster renders reserved add/remove slots (inert) so cut 2 needs no
  layout redesign.

## Design Review — Decisions (2026-07-04, /plan-design-review)

Reviewed against DESIGN.md ("Family Chronicle") with visual mockups from the gstack
designer. **Mockups are content-and-layout references only** — the designer invented a
masthead/crest/nav that do NOT match the real app. The real page lives inside the
existing chrome and re-skins per theme. Starting design-completeness 4/10 → target 10.

### Locked layout — master-detail dossier + bottom-sheet family
- **Chrome is reused, not reinvented.** The page renders inside the existing `AppFrame` /
  `AppBar`; it does not draw its own header, masthead, or crest (DESIGN.md: **no crest**).
  It re-skins with the active **Film (default)** and **Classic** themes via the token set.
- **Enable the nav slot that already exists.** `TabNav.vue` already defines a `members`
  tab with `enabled: false`. Enabling = set `enabled: true`, `to: '/members'`, and extend
  the `activeId` computed to map the `members` route to the active tab.
- **Left index (roomy).** A generous-width search field (placeholder "Search name or
  place…") with a small row of filter/sort controls beneath it; scrollable member rows =
  small oval portrait + full name (Cinzel) + years (EB Garamond italic), **wide enough for
  long ru/be names on two lines**. A total-count footer ("N members").
- **Center dossier (vertical scroll), in order:** (1) header = medium portrait medallion +
  name + lifespan + a prominent **"Find on tree"** button; (2) editable field tablets;
  (3) **Biography** (the largest section); (4) **Residences** list; (5) **Photos/Gallery**.
- **Family = a bottom sheet** that slides up over the dossier with a drag handle. **Peek
  state** shows Parents + Spouse + Children; **expanded** (capped at ~half the viewport)
  additionally reveals Siblings. Relative cards are **roomy** (hold long ru/be names), and
  Siblings/Children **wrap/scroll to hold 10+**. Inert dashed "Add …" slots render as the
  cut-2 seam. Maps cleanly to mobile (a bottom sheet is native there).

### Correct field set (was wrong in the first mockups)
Editable scalar fields, matching the real `PersonDetail`: **Given name, Surname, Maiden
name** (each ru/be/en), **Sex** (enum dropdown), **Birth** (date + place), **Death** (date +
place), **Vocation** (enum + `VocationIcon`). The invented "Faith"/"Notes" fields are
dropped. Places on birth/death are `LocalizedText`.

### Sections the first plan under-specified — now decided
- **Biography** is first-class and can be up to ~10,000 chars — a prominent, scrollable
  panel; editors use the existing `BiographyEditor` (tabbed ru/be/en) inline. Not a "notes"
  tablet.
- **Residences** — a list editor of up to ~10 rows `{ place (ru/be/en), fromYear, toYear,
  mapUrl }`, own scroll area, add/edit/delete rows, a map-pin link. The **on-map city
  picker stays deferred** to cut 2 (needs a geocoding/map lib); cut 1 edits `mapUrl` + place
  text.
- **Photos/Gallery** — reuse `PersonPhotos.vue` verbatim (`{ detail, canEdit, name }`): the
  unified 5-item grid (portrait + gallery + living-portrait video tile), upload / set
  portrait / remove / hide-seed for editors, read-only for visitors. (Was missing entirely.)
- **Find on tree** — button navigates to `/` (Tree) focused on the person (reuse the
  existing focus mechanism / `/person/:slug` deep link).

### Search — broadened
Extend beyond names: match **maiden name AND residence place names**, in the active locale.
**Data wrinkle:** residences live on `PersonDetail`, not the `PersonSummary` graph the
roster loads — so residence search needs residence data available client-side (either add
place text to the members list payload, or a dedicated members endpoint). Decide the data
source before wiring search. Name-only search still works from the existing predicate.

### Interaction states (must be designed, not defaulted)
- **Index:** loading (skeleton rows), empty ("no members match" with a clear-search
  action), error (retry). Row states: hover, focus-visible, selected.
- **Inline field edit:** idle → editing → **dirty** → **saving** → **saved**, plus a
  **validation-error** display per field (bad year range, all-null name). Resilient save
  like `BiographyEditor` (optimistic + recover on failure).
- **Bottom sheet:** collapsed / peek / expanded; a relative with no photo shows the cameo
  placeholder; empty relation shows the inert add-slot.

### Visual hierarchy
Index row: **name** primary, years secondary, portrait as a scan anchor. Dossier eye-path:
portrait+name → Find-on-tree → fields → biography → residences → gallery → (family on
demand). One job per section; sections separated by the gilt hairline rule.

### Responsive / mobile
No three-column layout. On phone the index and dossier **stack** as list → detail (back
navigation between them); the family bottom sheet is native mobile behavior; touch targets
≥44px; the residences/relatives areas scroll within the sheet/panels.

### Accessibility
Keyboard nav for the index (arrow keys move selection, Enter opens); focus moves into the
detail on select and into the sheet on open (focus trap while expanded, Esc closes);
ARIA roles/labels on the sheet, the field editors, and the search filters; theme contrast
verified for both Film and Classic; all edit controls labelled.

## Eng Review — Decisions (2026-07-06, /plan-eng-review)

Architecture/code/test/perf review + an independent outside-voice challenge. These
decisions **update and, where noted, supersede** the sections above. Scope locked to
**all three levers**: stage 1a (read-only page + backend override slice proven by curl)
→ 1b (scalar-field editor); defer residence-place **search** (ship name + maiden search);
**years-first** (defer birth/death place editing).

### Backend — profile override
- **Merge applies only the editable scalar subset**, field-by-field, in the same
  `FamilySnapshotProvider.Select` that layers biography then media. The override record
  carries **only** names/sex/birth/death-year/vocation — never biography or portrait — so a
  profile override can't clobber a bio/media override (disjoint fields; add a test that
  proves bio + media survive a profile save).
- **Name-field semantics (Finding 2):** the editor **pre-fills every locale from current
  merged state and submits the complete set** (like `BiographyEditor`'s tabs), so
  whole-record-latest-wins never drops a locale. The merge's **null-locale → seed fallback**
  stays as defense-in-depth. Representing an *intentional* empty distinct from "inherit seed"
  is **out of cut 1** (see revert-to-seed below + TODO).
- **Revert-to-seed per field (outside-voice #1, now in cut 1 — was deferred):** each
  overridable field gets a **"clear override → fall back to seed"** action, mirroring how the
  re-selectable seed photo tile already reverts a portrait. This kills the *permanence/fossil*
  problem: because `family.json` is the canonical dataset the owner keeps hand-editing, an
  override that permanently shadows the seed would silently swallow a later seed correction of
  the same field. Revert also doubles as the escape hatch for clearing a locale.
- **Cross-entity validation in the handler (outside-voice #3):** beyond single-record rules
  (birth ≤ death, plausible year bounds, ≥1 name locale, id `^p-\d+$`), the handler reads the
  merged snapshot and **rejects a birth year that precedes a parent's or postdates a child's**,
  via a small `IFamilyGraphValidator` domain service so the handler stays thin. Keep a cheap
  defense-in-depth test that the layout renders impossible data without crashing (it already
  tolerates null years).
- Endpoint/command/handler/validator mirror the biography trio; save calls
  `RefreshAsync` to rebuild the snapshot immediately.

### Frontend
- **Cache coherence = hybrid (Finding 1):** after a successful profile save, **patch
  display-only fields (names/sex/vocation) in place** in `familyStore`, and **refetch the
  graph (`store.load()`) only when a layout-affecting field changed** (birth year — and death
  year if it affects lifespan rendering), so the oak re-lays-out. The in-place patch must
  mirror the backend merge exactly so the two can't drift. (Copying the photo fast-path
  wholesale would leave the tree stale — a second, client-side split-brain.)
- **`useRelatives(personId)` composable (Finding 3):** pure, unit-tested derivation of
  `{parents, siblings, spouses, children}` from people + unions (edge cases: no parents,
  multi-union, half-sibling = shares ≥1 parent, self-reference). `RelativeCluster.vue` only
  renders. Build a memoized `parentId → children` index once rather than re-scan per relative.
- **Family area — layout ready, no visible inert slots (outside-voice #5a; supersedes the
  "reserved empty slots rendered but inert" wording above):** the cluster layout accommodates
  future add/remove affordances (spacing + a stubbed slot component), but **cut 1 renders no
  dashed "add" UI**. Honors the seam intent without shipping speculative UI wired to nothing.

### Scope moves
- **Residence editing → its own later cut (1c) (outside-voice #5b):** residences are a
  variable-length list of structured i18n records, not a scalar field, and editing a place
  with no picker is rough. Cut 1b = **scalar fields only** (names/sex/years/vocation).
  Residences still **display read-only** in cut 1; the list editor rides with the map-picker
  cut.
- **Staging is risk-first (outside-voice #4):** the backend override slice + its curl proof
  is the riskiest work and **leads 1a** (can be its own PR before the read-only page), so the
  snapshot-merge design is validated before any editor UI is built.
- **Concurrency (outside-voice +1):** whole-record latest-wins can let two tabs clobber each
  other silently. Accepted for a solo archive; **TODO:** add a revision precondition
  (optimistic concurrency) if editing ever goes truly multi-editor.

### NOT in scope (cut 1)
- Add-person / delete-person and any relationship editing — cut 2 (override store only
  modifies existing seed ids; orphan can't be placed).
- Residence editing + map-based place picker — cut 1c.
- Residence-place **search** — name + maiden only (removes the graph-payload data decision).
- Birth/death **place** editing — years-first.
- Intentional-empty-locale sentinel (distinct from seed-inherit) — deferred; revert-to-seed
  covers the clear case.
- Multi-editor optimistic-concurrency preconditions — deferred (solo).
- Animated census-card shuffle (Approach C) — banked north star.
