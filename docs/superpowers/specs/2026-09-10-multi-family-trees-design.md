# Design: Multiple family trees — switching between families and following marriage links

Generated by /brainstorming on 2026-09-10
Branch: claude/family-tree-switching-ee48f8
Repo: family-tree (perovsky.family)
Status: APPROVED

## Problem Statement

The app renders exactly one family. `FamilyData:Source` names a single seed, a singleton
`FamilySnapshotProvider` holds one merged graph, override and media keys are bare person
ids, and no route carries a family identity. A person who married into this family is
flagged only by `marriedIntoFamily: true` — a dead end. Their own lineage, if it is
chronicled at all, is unreachable.

We want two things:

1. **Follow a marriage across trees.** A member card offers a button to open the family
   tree that person came *from* (`origin`) or left *for* (`joined`), landing on that same
   person in the other tree when the counterpart is known.
2. **Switch trees deliberately.** A visitor can pick any available family tree from the
   settings menu, independent of any particular member.

## Decisions

Settled during brainstorming; recorded so the plan does not relitigate them.

| Question | Decision |
|---|---|
| Storage shape | One seed file per family, each with its own id-space |
| Family discovery | A `families.json` registry beside the seeds |
| Cross-family link | An explicit `familyLinks` array on the person, both directions |
| URL shape | Default family unprefixed; others under `/f/:familyId` |
| Editing scope | Family-scoped storage keys, one shared editor allow-list |
| Existing data | Default family keeps bare keys forever; no migration |
| Family id transport | Path prefix on the API, current routes aliased to the default |
| Snapshot holding | A registry of per-family `FamilySnapshotProvider`s |

## Data

### The registry — `families.json`

Sits beside the seeds at the same source root (`Data/` locally, `gs://…/` in deployment),
located by a new `FamilyData:Registry` setting.

```json
{
  "defaultFamily": "perovsky",
  "families": [
    { "id": "perovsky", "source": "family.json",
      "name": { "ru": "Перовские", "be": "Пяроўскія", "en": "Perovsky" } },
    { "id": "kowalski", "source": "kowalski.json", "mediaPrefix": "portraits/kowalski",
      "name": { "ru": "Ковальские", "be": "Кавальскія", "en": "Kowalski" } }
  ]
}
```

- `source` resolves relative to the seed root, so adding a family is an upload plus one
  registry line — preserving today's swap-without-redeploy property.
- `id` matches `^[a-z0-9-]+$`. A duplicate id or an unknown `defaultFamily` fails startup
  loudly (`LogError` + throw), consistent with the existing fail-fast seed load.
- `mediaPrefix` is optional; see *Media*.
- **Back-compat:** with no registry file present, the API synthesizes a one-family
  registry from the existing `FamilyData:Source` with id `default`. Local dev, the test
  fixtures, and the current deployment keep working untouched until a registry is uploaded.

### Cross-family links on a person

A new optional array in the seed, mapped onto `Person`:

```json
"familyLinks": [
  { "family": "kowalski", "personId": "p-0042", "relation": "origin" }
]
```

- `relation` is `origin` (married *into* this family from there) or `joined` (left this
  family *for* there).
- `personId` is optional — without it the switch lands on that family's default root.
- Links are **one-way as authored**. The reciprocal link is deliberately not derived: the
  other seed may legitimately not contain the person, and inventing a link would produce a
  button that leads nowhere.
- A link naming a family absent from the registry is dropped at snapshot build with a
  `LogWarning`, so the button never renders rather than 404-ing on click.

## Backend

### API surface

Canonical routes carry the family; today's routes remain as aliases for the default family,
so every existing bookmark, the Cloudflare `/api/*` proxy, and the health check keep working.

| Route | Meaning |
|---|---|
| `GET /api/families` | Registry: id, localized name, `isDefault` |
| `GET /api/families/{familyId}/graph` | That family's merged graph |
| `GET /api/families/{familyId}/people/{id}` | Person detail |
| `GET/PUT /api/families/{familyId}/people/{id}/biography` | Biography |
| `GET/PUT /api/families/{familyId}/people/{id}/profile` | Profile fields |
| `POST/DELETE /api/families/{familyId}/people/{id}/photos…` | Photo manager |
| `GET /api/family/graph`, `/api/people/…` | Unchanged aliases → default family |

An unknown `familyId` returns 404 before any load is attempted.

### `FamilySnapshotRegistry`

A new singleton holding one `FamilySnapshotProvider` per registered family, created lazily
on first request for that family and cached thereafter. `FamilySnapshotProvider` itself is
**unchanged** — its refresh lock, TTL, last-good fallback, and consecutive-failure counter
are the only concurrency-sensitive code in the repo and stay untouched. Each family's
provider needs its own `IFamilyDataLoader` bound to that family's `source`, so loader
construction moves behind a small factory (`IFamilyDataLoaderFactory`) that picks the GCS
or JSON loader per source URI exactly as `AddInfrastructure` does today.

Consequences that fall out for free: providers refresh independently, and an unreachable
second seed degrades only its own tree.

### Health

`/health` keeps reporting the default family's source as today (so the deploy gate is
unchanged) and adds a per-family roll-up, making a broken secondary seed visible without
failing the check for the whole site.

### Storage keys

Per the migration decision, the default family keeps bare keys forever. One helper:

```
OverrideKey(familyId, personId) => familyId == default ? personId : $"{familyId}/{personId}"
```

used by the Firestore override store and the R2 upload paths, so the asymmetry lives in one
tested place. **Known consequence, documented at the helper and in the reference docs:**
promoting a different family to default later would orphan the existing bare-keyed
overrides. Accepted now; the fix would be a one-time rewrite at that point.

## Media

Two media namespaces exist today, both flat and family-blind: seed portraits stored as a
bare filename under an implicit `portraits/` prefix, and uploads at
`uploads/{personId}/{hash}.webp`. Both collide across families, since every seed has a
`p-0001`.

The family dimension is added **entirely on the backend**, riding the rule that already
exists in `resolveMediaUrl` — a reference containing a slash is a full key, served verbatim.
`resolveMediaUrl` and the `/media/[[path]]` Pages Function therefore need **no change**
(`resolveMediaKey` already accepts arbitrarily nested keys; it rejects only empty segments,
`.`/`..`, backslashes and trailing slashes).

| | default family | other families |
|---|---|---|
| seed portrait | `portraits/p-0001.jpg` (bare, as today) | `portraits/kowalski/p-0001.jpg` |
| upload | `uploads/p-0001/{hash}.webp` (as today) | `uploads/kowalski/p-0001/{hash}.webp` |

1. **Seed expansion at snapshot build.** For a non-default family, a bare `portrait`,
   `portraitThumb`, `portraitVideo`, or gallery filename is rewritten to
   `{mediaPrefix}/{name}` (default `portraits/{familyId}`) before the graph leaves the
   backend. A reference already containing a slash passes through untouched.
2. **`MediaKeyGenerator.ForPerson` gains a `familyId`**, emitting the prefixed key for
   non-default families. Existing uploads keep their keys and keep resolving.
3. **No tooling change.** `scripts/upload-media.mjs` mirrors the local `media/` folder to
   object keys one-to-one, so a second family's portraits are dropped in
   `media/portraits/kowalski/` and uploaded as-is.

The 5-item media cap and the seed-tile / hidden-seed logic key off the person within one
snapshot and are unaffected — a prefixed key is still just a key.

## Frontend

### Routing

Two shapes per view, sharing components:

```
/                  /f/:familyId
/chronicle         /f/:familyId/chronicle
/members/:slug?    /f/:familyId/members/:slug?
/person/:slug      /f/:familyId/person/:slug
```

A single resolver reads `route.params.familyId ?? registry.defaultFamily`.
`installFirstVisitRedirect` keys its tree check on both route names, so a first visit to
`/f/kowalski` still lands on that family's chronicle. An unknown or unregistered
`familyId` renders the existing error state with a link back to the main tree.

### Stores

- New `familiesStore`: the registry list plus `activeFamilyId`, fetched once on boot from
  `/api/families`.
- `familyStore.load(familyId)` takes the family and passes it to every `familyApi` call.
- Switching **resets** `familyStore` (people, unions, focus) and `selectionStore` rather
  than merging, so no stale medallion or selection survives a switch.
- `panelStore`, theme, and locale persist across a switch — viewer preferences, not family
  data.

### The member-card button

`PersonHeader.vue` already hosts "Open in members" and is shared by the tree popup and the
members dossier; the cross-family buttons join that row. They render from
`detail.familyLinks` filtered against the loaded registry, one per surviving link:

- `origin` → `family.openOrigin` — "Kowalski family tree"
- `joined` → `family.openJoined` — "Family they joined: …"

with the localized family name interpolated.

Clicking pushes `{ name: 'person', params: { familyId, slug } }` when the link carries a
`personId`, else that family's root route. The friendly slug cannot be built here — it is
derived from name and birth year, which live in a graph that is not loaded yet — so the
**bare person id is used as the slug**. That is already a valid slug: `extractPersonId`
matches `p-<digits>$`, and a bare id is exactly that. Once the target family's graph has
loaded, the view canonicalises the URL to the friendly slug with `router.replace`, so the
address bar ends up identical to an in-app navigation without adding a history entry.
Being a normal router push, Back returns to the previous tree.

### The general switcher

A "Family tree" group in `SettingsMenu` — already the home of theme and locale, and already
rendered in both the desktop dropdown and the mobile sheet — listing every registered family
with the active one marked. Hidden entirely when the registry holds one family, so today's
single-family UI is visually unchanged.

## Testing

**Backend**
- Registry parse and validation: duplicate id, unknown `defaultFamily`, bad id format,
  missing file → synthesized single-family registry.
- `FamilySnapshotRegistry`: lazy creation, per-family caching, isolation (a failing second
  seed must not degrade the default family's snapshot).
- Alias routes return the same payload as the explicit default-family routes.
- `OverrideKey` on both branches; `MediaKeyGenerator` on both branches.
- Seed media expansion: bare name on a non-default family → prefixed; already-slashed →
  untouched; default family → unchanged.
- `familyLinks`: unregistered family dropped with a warning; link without `personId` kept.

**Frontend**
- Family-id resolution from both route shapes, including the first-visit redirect.
- Store reset on switch (no stale people/selection).
- Button visibility: link + registered family → shown; registered but no `personId` → shown,
  routes to root; unregistered → hidden.
- A bare person id round-trips as a slug, and the target view replaces it with the friendly
  slug once the graph loads (without adding a history entry).
- Switcher hidden with a single-family registry.

Fixtures gain a small second-family seed and a two-family registry.

## Documentation

Lands in the same PR, per the repo's docs-with-the-PR rule: `docs/reference/` gains the new
endpoints, the `families.json` format, the `familyLinks` field, and the media key layout;
the CLAUDE.md and README overviews pick up multi-family.

## Out of Scope

- Per-family editor allow-lists (the shared allow-list stands; the family-scoped keys mean
  this can be added later without a storage migration).
- Deriving reciprocal `familyLinks` automatically.
- Cross-family search or a combined view spanning families.
- Migrating the default family's bare override keys.
