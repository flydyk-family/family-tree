# Design: Multiple family trees — switching between families and following marriage links

Generated by /brainstorming on 2026-09-10
Branch: claude/family-tree-switching-ee48f8
Repo: family-tree (perovsky.family)
Status: APPROVED — revised 2026-09-11 after plan review

> **Revision 2026-09-11.** A code-verified review of the first implementation plan found
> defects that change three decisions here: the override key format (Firestore document ids
> cannot contain `/`), how a seed photo is recognised (the "no `/` means seed" rule breaks
> once other families' seed names carry a prefix), and the person-id format (validators
> require `p-<digits>`). It also settled the internal mechanism for carrying the family
> through a request, and split delivery into four PRs. Changed passages are marked *(rev.)*.

## Problem Statement

The app renders exactly one family. `FamilyData:Source` names a single seed, a singleton
`FamilySnapshotProvider` holds one merged graph, override and media keys are bare person
ids, and no route carries a family identity. A person who married into this family is
flagged only by `marriedIntoFamily: true` — a dead end. Their own lineage, if it is
chronicled at all, is unreachable.

We want two things:

1. **Follow a marriage across trees.** A member card offers a button to open the family
   tree that person came *from* (`origin`) or left *for* (`joined`), landing on that same
   person in the other tree when the counterpart is known.
2. **Switch trees deliberately.** A visitor can pick any available family tree from the
   settings menu, independent of any particular member.

## Decisions

Settled during brainstorming and review; recorded so the plan does not relitigate them.

| Question | Decision |
|---|---|
| Storage shape | One seed file per family, each with its own id-space |
| Family discovery | A `families.json` registry beside the seeds |
| Cross-family link | An explicit `familyLinks` array on the person, both directions |
| URL shape | Default family unprefixed; others under `/f/:familyId` |
| Editing scope | Family-scoped storage keys, one shared editor allow-list |
| Existing data | Default family keeps bare keys forever; no migration |
| Family id transport | Path prefix on the API, current routes aliased to the default |
| Snapshot holding | A registry of per-family `FamilySnapshotProvider`s |
| Override key format *(rev.)* | `{familyId}__{personId}` for non-default families |
| Seed recognition *(rev.)* | A media reference is a seed unless it starts with `uploads/` |
| Person ids *(rev.)* | Every family uses `p-<digits>` ids, as today |
| Family inside a request *(rev.)* | A scoped `IFamilyContext`; handlers and repositories stay family-agnostic |
| Delivery *(rev.)* | Four PRs, each safe to deploy on its own |

## Data

### The registry — `families.json`

Located by a new `FamilyData:Registry` setting (a local path or a `gs://` URI).

```json
{
  "defaultFamily": "perovsky",
  "families": [
    { "id": "perovsky", "source": "family.json",
      "name": { "ru": "Перовские", "be": "Пяроўскія", "en": "Perovsky" } },
    { "id": "kowalski", "source": "kowalski.json", "mediaPrefix": "portraits/kowalski",
      "name": { "ru": "Ковальские", "be": "Кавальскія", "en": "Kowalski" } }
  ]
}
```

- *(rev.)* A relative `source` resolves **against the registry's own location** — beside
  the registry file locally, or in the same bucket and folder for a `gs://` registry. An
  absolute path or a `gs://` URI is used as-is. Adding a family is an upload plus one
  registry line, preserving today's swap-without-redeploy property.
- *(rev.)* The registry is read **once, synchronously, at startup**, from local disk or GCS,
  and held as a singleton. Changing it is a deployment-level act, unlike the seed contents,
  which still refresh on the snapshot TTL.
- `id` matches `^[a-z0-9-]+$`. A duplicate id, an unknown `defaultFamily`, a missing
  `source`, or an empty list fails startup loudly (`LogError` + throw), consistent with the
  existing fail-fast seed load.
- `mediaPrefix` is optional; see *Media*.
- **Back-compat:** with no `FamilyData:Registry` configured, the API synthesizes a one-family
  registry from the existing `FamilyData:Source` with id `default`. Local dev, the test
  fixtures, and the current deployment keep working untouched until a registry is uploaded.

### Person ids *(rev.)*

Every family's seed uses `p-<digits>` person ids, exactly like today's seed. Ids only have
to be unique within one family, so two families may both contain `p-0001`. Four request
validators and the SPA's slug parser already depend on this shape, so it is a documented
seed rule rather than a code change. A seed person whose id breaks the rule is logged as a
warning at snapshot build.

### Cross-family links on a person

A new optional array in the seed, mapped onto `Person`:

```json
"familyLinks": [
  { "family": "kowalski", "personId": "p-0042", "relation": "origin" }
]
```

- `relation` is `origin` (married *into* this family from there) or `joined` (left this
  family *for* there). The API emits it lowercase.
- `personId` is optional — without it the switch lands on that family's default root.
- Links are **one-way as authored**. The reciprocal link is deliberately not derived: the
  other seed may legitimately not contain the person, and inventing a link would produce a
  button that leads nowhere.
- A link naming a family absent from the registry is dropped at snapshot build, so the
  button never renders rather than 404-ing on click. *(rev.)* This is logged at Warning on a
  family's first build and at Debug afterwards, so a single-family deployment whose seed
  carries links doesn't log noise every TTL.

## Backend

### API surface

Canonical routes carry the family; today's routes remain as aliases for the default family,
so every existing bookmark, the Cloudflare `/api/*` proxy, and the health check keep working.

| Route | Meaning |
|---|---|
| `GET /api/families` | Registry: id, localized name, `isDefault` |
| `GET /api/families/{familyId}/graph` | That family's merged graph |
| `GET /api/families/{familyId}/people/{id}` | Person detail |
| `GET/PUT /api/families/{familyId}/people/{id}/biography` | Biography |
| `GET/PUT /api/families/{familyId}/people/{id}/profile` | Profile fields |
| `POST/DELETE /api/families/{familyId}/people/{id}/photos…` | Photo manager |
| `GET /api/family/graph`, `/api/people/…` | Unchanged aliases → default family |

An unknown `familyId` returns 404 before any seed is loaded. *(rev.)* The larger request-body
cap for photo uploads applies to both the aliased and the family-scoped upload routes.

### The family inside a request *(rev.)*

A scoped `IFamilyContext` carries the request's family. It defaults to the registry's
default family and is overwritten by a small middleware when the matched route has a
`familyId` value; an unregistered id short-circuits with a 404. Two scoped registrations
resolve from it:

- `IFamilySnapshotProvider` → that family's provider from `FamilySnapshotRegistry`.
- `IPersonOverrideStore` → a `FamilyScopedOverrideStore` wrapping the real store for that
  family.

Because of this, the repositories, `FamilyQueryService`, and every existing MediatR handler
stay family-agnostic and unchanged.

### `FamilySnapshotRegistry`

A singleton holding one `FamilySnapshotProvider` per registered family, created on first
request for that family and cached thereafter. The provider's refresh lock, TTL, last-good
fallback, and consecutive-failure counter are unchanged. Each provider gets:

- its own `IFamilyDataLoader`, bound to that family's source through a small
  `IFamilyDataLoaderFactory`, which picks the GCS or JSON loader per source URI as
  `AddInfrastructure` does today;
- a `FamilyScopedOverrideStore` for its family, wrapping the raw singleton store (never the
  scoped registration).

Consequences that fall out for free: providers refresh independently, and an unreachable
second seed degrades only its own tree. The startup warm-up refreshes the default family's
provider through the registry, keeping today's fail-fast seed load.

### Health

`/health` keeps its current verdict, tracking the default family's provider only, so the
deploy gate is unchanged. *(rev.)* The report body adds `degradedFamilies`: the ids of every
created provider that is currently degraded. A broken secondary seed is then visible without
failing the check for the whole site.

### Storage keys *(rev.)*

The default family keeps bare keys forever. One helper class owns the rule:

| Helper | Default family | Other families |
|---|---|---|
| `OverrideKey` (Firestore doc id) | `p-0001` | `kowalski__p-0001` |
| `UploadPrefix` (R2 object keys) | `uploads/p-0001` | `uploads/kowalski/p-0001` |

The `__` separator exists because Firestore document ids cannot contain `/`. It is
unambiguous because family ids cannot contain `_` and person ids are `p-<digits>`, and it
never matches Firestore's reserved `__…__` pattern. R2 keys are plain object names, so the
upload prefix keeps its `/`.

`FamilyScopedOverrideStore` applies `OverrideKey` to every single-person call. It filters
each map getter to its own family: the default family owns keys without `__`, and another
family owns the keys starting `{familyId}__`, returned with that prefix stripped.

**Known consequence, documented at the helper and in the reference docs:** promoting a
different family to default later would orphan the existing bare-keyed overrides and uploads.
That is accepted now; the fix would be a one-time key rewrite at that point.

## Media

Two media namespaces exist today, both flat and family-blind: seed portraits stored as a
bare filename under an implicit `portraits/` prefix, and uploads at
`uploads/{personId}/{hash}.webp`. Both collide across families, since every seed has a
`p-0001`.

The family dimension is added on the backend, riding the rule that already exists in
`resolveMediaUrl`: a reference containing a slash is a full key, served verbatim. That
function and the `/media/[[path]]` Pages Function need no change, since `resolveMediaKey`
already accepts nested keys.

| | default family | other families |
|---|---|---|
| seed portrait | `portraits/p-0001.jpg` (bare, as today) | `portraits/kowalski/p-0001.jpg` |
| upload | `uploads/p-0001/{hash}.webp` (as today) | `uploads/kowalski/p-0001/{hash}.webp` |

1. **Seed expansion at snapshot build.** For a non-default family, a bare `portrait`,
   `portraitThumb`, `portraitVideo`, or gallery reference is rewritten to
   `{mediaPrefix}/{name}` (default `portraits/{familyId}`) before the graph leaves the
   backend. A reference already containing a slash passes through untouched.
2. **Upload keys** come from `MediaKeyGenerator.ForPerson`, which gains the family and uses
   `UploadPrefix`. Existing uploads keep their keys and keep resolving.
3. **Seed recognition *(rev.)*.** Today the promote, delete, and suppress-seed handlers and
   the SPA photo grid treat "no `/`" as "this is a seed". Expansion gives other families'
   seeds a `/`, which would make them look like uploads. Promoting would duplicate the
   image, hiding would silently fail, and deleting could remove the real seed object from
   R2. Every one of those checks moves to a single rule: **a reference is an upload if and
   only if it starts with `uploads/`**. This is `StorageKeys.IsUploadKey` in the backend and
   `isUploadKey` in the SPA. For the default family the rule is equivalent to today's check,
   because no default seed reference contains a `/`.
4. **No tooling change.** `scripts/upload-media.mjs` mirrors the local `media/` folder to
   object keys one-to-one, so a second family's portraits go in `media/portraits/kowalski/`.

The 5-item media cap and the seed-tile / hidden-seed logic key off the person within one
snapshot. Seed tiles and `HiddenSeeds` both see the expanded reference, so they stay
consistent with each other. Changing a family's `mediaPrefix` later would orphan that
family's hidden-seed entries; the reference docs note this.

## Frontend

### Routing

Two shapes per view, sharing components:

```
/                  /f/:familyId
/chronicle         /f/:familyId/chronicle
/members/:slug?    /f/:familyId/members/:slug?
/person/:slug      /f/:familyId/person/:slug
```

The active family is **always derived from the route**: its `familyId` param, or the
default family on the unprefixed routes. The first-visit redirect sends a first visit to
`/f/kowalski` to that family's chronicle. *(rev.)* Every in-app navigation goes through one
helper, `familyLocation(view, familyId, params)`, which produces the prefixed or unprefixed
location. This covers the ten existing bare-route-name navigations and the new buttons. A
link to the default family always uses the unprefixed routes, so `/f/{defaultId}/…` is never
generated. An unknown or unregistered `familyId` shows the view's existing error state plus a
link back to the main tree.

### Loading and state *(rev.)*

- New `familiesStore`: the registry list, fetched once on boot from `/api/families`. A
  failure leaves an empty registry, which renders as a single-family app.
- `familyStore.ensureFamily(familyId)` is the single entry point for loading. It does nothing
  when that family is already loaded or loading. Otherwise it resets `familyStore`, clears
  `selectionStore` (whose cache is keyed by person ids that are only unique within one
  family), and closes `panelStore`'s person panels, then loads the family. A request token
  discards a stale response that arrives after a newer switch.
- A router `afterEach` hook calls `ensureFamily` for every committed navigation, which covers
  switches within one view. It runs before any component watcher reacts, so per-family state is
  already reset when a view sees the new route. Each view still calls it on mount, which is
  idempotent.
- On a switch, `TreeView` still loads the newly selected person's detail but skips its own URL
  rewrites, because the route already names the target. It rewrites to a friendly slug only once
  that person is known.
- Theme, locale, orientation, and the stats panel persist across a switch — viewer
  preferences, not family data.
- Every API client that names a person — the read calls and the biography, profile, and
  photo edit calls — takes the family and uses the family-scoped route. Otherwise an edit in
  another family would land on the default family's person with the same id.

### The member-card button

`PersonHeader.vue` already hosts "Open in members" and is shared by the tree popup and the
members dossier; the cross-family buttons join that row. They render from
`detail.familyLinks` filtered against the loaded registry, one per surviving link, labelled
`family.openOrigin` / `family.openJoined` with the localized family name.

Clicking navigates to the linked person when the link carries a `personId`, else to that
family's root. The friendly slug cannot be built here, because name and birth year live in a
graph that isn't loaded yet. So the **bare person id is used as the slug**, which is already
valid: `extractPersonId` matches `p-<digits>$`. `TreeView`'s existing canonicalising watcher
then replaces it with the friendly slug once the graph loads, without adding a history entry.
Back returns to the previous tree.

### The general switcher

A "Family tree" group at the top of the settings panel lists every registered family, with
the active one marked. The settings panel is already rendered in both the desktop dropdown
and the mobile sheet. The group is hidden when the registry holds one family, so today's
single-family UI is visually unchanged.

## Delivery *(rev.)*

Four PRs, merged in order, each branched off `main` after the previous one lands and each
carrying its own documentation:

1. **Backend foundation.** Registry, storage keys, `familyLinks`, the snapshot registry, the
   family context, the override wrapper, and the seed-recognition rule. No behaviour change
   while no registry is configured.
2. **Family-scoped API.** The new routes, the upload cap, family-scoped upload keys, the
   health roll-up, and the two-family dev fixtures. The registry is opt-in.
3. **Switching in the SPA.** The registry store, family-aware API clients, routing and
   navigation, loading and state reset, and the switcher. The switcher only appears when more
   than one family is registered.
4. **Cross-family member links.** The member-card buttons, the reciprocal dev link, and the
   end-to-end check.

Production changes only when a `families.json` is uploaded and `FamilyData:Registry` is set.

## Testing

**Backend**
- Registry parse and validation: duplicate id, unknown `defaultFamily`, bad id format,
  missing `source`, empty list, source resolution (local and `gs://`), and the synthesized
  single-family fallback.
- `StorageKeys`: every helper on both branches, including `IsUploadKey`.
- `FamilyScopedOverrideStore`: key translation and map filtering in both directions, so the
  default family never sees `kowalski__…` keys and Kowalski never sees bare ones.
- `FamilySnapshotRegistry`: lazy creation, per-family caching, and isolation (a failing
  second seed must not degrade the default family's snapshot).
- Seed normalisation: media expansion, dropped unregistered links, and the id-shape warning.
- Promote, delete, and suppress-seed handlers with a prefixed seed reference, proving that
  seeds are still recognised and a seed object is never deleted.
- Middleware: family from the route, default fallback, and 404 for an unknown family.
- Integration: alias routes match the default-family routes. With a two-family fixture: the
  second family's graph is distinct, editing it does not touch the default family, uploads
  on the family route pass the size cap, and an unknown family returns 404.

**Frontend**
- Route shapes, `familyLocation`, and the first-visit redirect for both shapes.
- `ensureFamily`: no-op when current, reset on a switch, and a stale response discarded.
- Every edit client targets the family-scoped route when given a family.
- Photo grid seed detection with a prefixed seed reference.
- Navigation inside `/f/kowalski` stays inside that family.
- Button visibility: link and registered family → shown; no `personId` → routes to root;
  unregistered → hidden. Default-family links use unprefixed routes.
- Switcher hidden with a single-family registry.

## Out of Scope

- Per-family editor allow-lists (the shared allow-list stands; the family-scoped keys mean
  this can be added later without a storage migration).
- Deriving reciprocal `familyLinks` automatically.
- Cross-family search or a combined view spanning families.
- Migrating the default family's bare override keys.
- Redirecting a hand-typed `/f/{defaultId}/…` URL to its unprefixed form (it works, just
  isn't canonical).
